Syllabus

R

R is an open-source programming language for data analysis, statistics, and graphics.

  • R is interpreted: it runs an expression and returns the result immediately.
  • One of R’s greatest strengths is its add-on package ecosystem. Packages add new methods, graphics, and data tools.
  • RStudio is the interface where we write and run R code.

R was created by Ross Ihaka and Robert Gentleman at the University of Auckland and first released in 1993.

RStudio: Source and Console

Source/editor pane

This is where you edit and save .qmd and .R files. It is the durable record of your work.

print(3 + 2)

For now, edit code inside a chunk and click its right-triangle play button to run it.

Console pane

The Console is the running R session. R interprets each expression and returns its result:

> print(3 + 2)
[1] 5

The Console is useful for quick tests. Put work you want to keep in the source file.

The other panes show objects in memory and provide access to files, plots, packages, and help.

Reading Today’s R Code

gap <- read_csv("Data/gapminder/gapminder.csv")

gap |>
  filter(year == 2007) |>
  summarize(median_life = median(lifeExp))
  • <- stores a result in an object; here the object is named gap.
  • A function does something. Its inputs go inside parentheses: filter(...).
  • |> passes the result of one step into the next step.

We will teach this syntax carefully. Today, you only need to recognize the parts and edit a value inside working code.

The Tidyverse: A Way of Working

The tidyverse is a consistent approach to organizing and processing data from inputs to outputs.

Tidy data:

  • each column describes one variable
  • each row describes one observation
  • each table contains one kind of observational unit

inputs → tidy data → transformation and analysis → outputs

dplyr supplies consistent verbs for processing data. ggplot2 turns tidy data into graphics.

Course Sequence

Two Parts

The semester has two parts.

  • Part I (weeks 1–10): AI is prohibited. Tidyverse, programming, git, the shell, APIs, Shiny — all by hand.
  • Part II (weeks 11–14): AI is required. Chat, copilots, agentic coding with Codex, LLMs as research instruments.

Part I: No AI

You cannot supervise a tool you cannot understand at a deep level.

AI coding tools are enormously productive for someone who can read code, debug it, and spot wrong output.

Without those skills, plausible-looking errors are difficult to recognize.

Why Part I Comes First

Part I gives you practice reading code, tracing errors, and checking output before we add AI tools.

By Part II, you’ll have specific ways to check the code and results an AI tool produces.

Plain Text vs. The GUI

A Common Research Workflow

The usual workflow: run the analysis, save figures to a folder, paste them into Word, build slides in PowerPoint, paste the figures again.

A co-author comments. Re-run. Save a new figure. Hunt down every place it appears. Replace. Repeat.

The analysis and the document are separate files, and every revision has to be copied across by hand.

Why We Use Plain Text

Everything in this course is plain text: .qmd, .R, .csv. Plain-text files have three useful properties:

  • Reproducible — the document is the analysis; render it and every number regenerates
  • Diffable — you can see exactly what changed, line by line, and who changed it
  • Durable — a text file opens in 2046 with no proprietary app
  • Amenable to AI — coding agents can read, edit, search, and test plain-text files directly

Example Diff

A one-character fix to a filter, seen as a diff:

-  filter(year == 2007)
+  filter(year >= 2000)

Word can track changes to prose. Plain-text files let version control track changes to the analysis as well. We start using that in Week 2.

Literate Programming

Knuth’s Definition

In 1984, Donald Knuth — the Stanford computer scientist behind TeX and The Art of Computer Programming — proposed literate programming:

Instead of imagining that our main task is to instruct a computer what to do, let us concentrate rather on explaining to human beings what we want a computer to do.

A program should be a piece of literature: prose for humans, with code woven through it, and one source that produces both the documentation and the running program.

From WEB to Your .qmd

Knuth built a system called WEB to write TeX itself this way. The idea took forty years to reach your laptop:

Year Tool What changed
1984 WEB Knuth: one file → typeset book and running program
2002 Sweave R code woven into LaTeX documents
2012 knitr Sweave rebuilt; R Markdown makes it mainstream
2022 Quarto language-agnostic, HTML/PDF/Word/slides/websites

Every .qmd you write this semester combines prose and executable code in one source file.

Why It Matters for Research

The same approach is useful for research:

  • a paper already combines prose and computation, so its source file can combine them too
  • the explanation sits next to the code it describes
  • the source remains readable when you return to the project months later

Knuth mails a check for $2.56 to anyone who finds an error in his books—one “hexadecimal dollar.”

A Reproducible Project

The Pipeline

Projects in this course follow this pipeline:

raw data → code → paper, report, presentation, or web app

The folders show which files are inputs, which are produced by code, and which are final outputs. A project may produce one of these forms or combine several of them.

Project Folders

my-project/
  Data/           # source data as received
  Processed/      # cleaned, analysis-ready data
  R/              # cleaning and helper scripts
  Images/         # figures produced by code
  Paper/          # paper source and bibliography
  Presentations/  # presentation source
  README.md
  my-project.Rproj

We will use two rules: source data are read-only (every fix lives in a script), and all paths are relative to the project (no C:/Users/boris/Desktop/...).

What Rendering Checks

Rendering checks whether the code runs from top to bottom in a fresh session.

The data, variable definitions, and interpretation need separate checks. A document can render successfully and still contain an error.

That’s why Part I teaches you to read code, and Part II teaches you to check the AI that writes it.

The Replication Standard

A research claim should travel with enough data, code, and instructions for another researcher to regenerate the result.

  • A finished PDF records the claim. The archive supplies the data and code that produced it.
  • Trying to use a replication archive reveals missing files, undocumented transformations, and hidden assumptions.
  • King (1995) made this a standard for quantitative political science. We return to it when Part II begins.

For this course, someone should be able to start from your repository, follow the README, and rebuild the paper without asking what you clicked.

Adjust RStudio to Fit You

Open Tools → Global Options and make these changes:

  1. Under Appearance, change the editor font size to one that is comfortable to read.
  2. Under Pane Layout, move at least one pane to a different location.
  3. Under General, set Save workspace to .RData on exit to Never.
  4. Under Code, check Highlight R function calls and Use native pipe operator, |>. We will explain both later.

Click Apply. If you finish early, browse the other options. Think about what they control and bring any questions to Thursday’s RStudio and Quarto session.
