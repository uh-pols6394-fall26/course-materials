The Mental Model

Four words from the reading

  • Repository (repo): the whole project folder — code, reports, figures, and appropriate data
  • Commit: a labeled snapshot of the whole project at a moment
  • Diff: the line-by-line difference between two snapshots
  • Tag: a name attached to an important commit, such as journal-submission

Git stores commits as a chain, so your project’s history is a string of snapshots. A useful mental model is a save point in a video game. We’ll recognize tags today but won’t create one.

Where your changes live: three places

  • Working directory — your files as they are right now
  • Staging area — changes you’ve marked for the next commit
  • History — commits already recorded

A commit moves changes: working directory → stage → history. The staging area is the part that feels strange at first; it lets you commit some changes now and hold others back.

Why begin in the Terminal?

  • For most people, RStudio’s Git controls will be more comfortable for everyday work.
  • We’ll start by typing the commands because each step is visible: inspect, stage, commit.
  • It is like learning arithmetic on paper before using a calculator. Understanding the mechanics makes the convenient tool easier to use correctly.
  • A short command is sometimes faster than navigating menus, and the same commands work on Posit Cloud, a laptop, or a server.

Then we’ll repeat the cycle with RStudio’s Git controls.

Later in the course, we’ll direct LLM coding agents to work with Git. An agent can inspect changes, create commits, restore files, and reverse a commit. The history lets you check its work and correct mistakes.

The Commit Cycle

Stage, then commit

git status              # what has changed?
git add .               # stage every unignored change here
git commit -m "Add project README"  # record the stage; -m supplies its label
  • add chooses what goes in; commit records it with a message
  • status is the command you will run most — run it constantly

Anatomy of a good commit message

  • The diff records the changed lines; the message explains the purpose of the change
  • Use a present-tense summary under ~50 characters
  • Good: Fix year parsing in cigarette data
  • Bad: changes, final, asdf
  • Write a message that will still make sense when you return six months later
  • One logical change per commit — not a whole day’s work in one blob

Use the name and email associated with your GitHub account. These become part of every commit you make in this Cloud project.

  • The first line stores the author name attached to commits.
  • The second stores the author email.
  • --global keeps each setting available throughout this Cloud project; quotation marks keep the full value together.

Run these once. They’re setup commands, and you don’t need to memorize them. Stop if the Terminal prints an error.

Start the repository

git init
git status
  • git init creates the hidden Git repository inside the current folder.
  • git status reports the repository’s state without changing anything.

Read the output before continuing. It should say:

  • On branch master
  • No commits yet
  • Untracked files

Git created a default branch called master. A branch is a named line of history. Today, every commit goes onto that line.

Untracked means git sees a file in the folder, but no commit contains it yet. The file is still there; git simply has no saved history for it.

Your Turn: record the first snapshot

git add . puts every unignored change in the current folder into the staging area. The period means “this folder.” It does not commit or upload anything.

Run one line, then read git status before moving on:

git add .
git status
git commit -m "Start Git practice project"
git status
  • The first line stages the files.
  • The second confirms what is staged.
  • git commit records the snapshot; -m supplies its quoted message.
  • The final status verifies that no changes remain outside the snapshot.

The commit message describes the starting project. The final status should say the working tree is clean.

Git prints a short report after the commit. The message should match yours; the remaining counts and file metadata can be ignored today.

History

Reading your history

git log --oneline

git log reads the commit history. --oneline displays each commit as one compact line.

a1c3f9e Add state policy import script
7b21d04 Add project README
3f88a10 Initial commit
  • Each line: a short commit ID plus your message
  • Parentheses such as HEAD -> master mark your current position; you can ignore them today
  • Plain git log shows full author, date, and message
  • Together, the messages provide a concise history of the project

Seeing what changed: diff

  • git diff — unstaged changes vs. the last commit
  • git diff --staged — what you’re about to commit
  • Lines marked - were removed, + were added
  • Focus on the - and + lines; ignore the header, hashes, and permission metadata today
  • The Diff button in the Git tab shows the same thing, in color

Read the diff before every commit. It’s your last check before you record something.

What Not to Track

.gitignore

Leave large raw data, rendered outputs, secrets, and system files out of version control. A .gitignore file lists patterns Git should skip.

.Rproj.user/
.Rhistory
*.html
Data/raw/
.Renviron

  • .Rproj.user/ is RStudio’s per-session project state.

  • .Rhistory is the Console command history.

  • *.html means every filename ending in .html; * is the wildcard.

  • Data/raw/ is the named raw-data folder and everything inside it.

  • .Renviron may hold credentials and must never enter Git history.

  • Commit the code that produces outputs; regenerate the outputs when needed

  • Plain-text files such as .R, .qmd, .md, and .csv produce readable line-by-line diffs

  • Git can store PDFs and images, but it cannot show their changes as useful line-by-line diffs

  • .Renviron holds secrets like API keys (Week 9) — never commit it

The supplied .gitignore

Open .gitignore and read it. This project already excludes RStudio session files, rendered HTML, distributed slides, .Renviron, and the evidence workbook.

You don’t need to edit it today. Inspect .gitignore before the first commit in an unfamiliar project.
