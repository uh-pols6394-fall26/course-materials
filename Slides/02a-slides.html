Why Version Control

What is version control?

Version control is a system for recording changes to a set of files over time.

  • Keep one working copy and record named checkpoints behind it
  • See what changed, when it changed, and who changed it
  • Restore an earlier version after a mistake
  • Combine several people’s work

Without it, revision history becomes filenames such as paper_draft.docx, paper_draft_v2_amy_comments.docx, and paper_draft_FINAL_v2_REALLY.docx.

What a shared folder leaves unresolved

A shared Dropbox folder makes exchanging files easy. Coordinating edits is still up to the people using it.

Suppose Boris and Amanda both open analysis.R:

  1. Boris changes the data-import code.
  2. Amanda adds validation checks.
  3. Both save without knowing the other is editing.

Dropbox may produce a conflicted copy or an overwritten change. Git preserves both contributions, shows the differences, and flags overlaps for Boris and Amanda to reconcile.

Git dominates version control

  • Git is the standard for most modern software and data projects; Subversion and Mercurial are alternatives.
  • Linus Torvalds created Git in 2005 to manage development of the Linux kernel.
  • Linux passed 40 million source-tree lines in 2025 and has involved many thousands of contributors.
  • Git lets those contributors work independently and combine their changes into a controlled history.

Linux kernel development process · 40-million-line milestone

GitHub dominates Git hosting

Git GitHub
Version-control software A web service built around Git
Runs where you are working Hosts remote copies of repositories
Records commits and diffs Shares and synchronizes repositories
Works without an internet connection Supports collaboration and off-site recovery

Other hosts include GitLab and Bitbucket. Linux uses Git but hosts its official repository at kernel.org.

GUI: graphical user interface Buttons, menus, and checkboxes

The Mental Model

Four words from the reading

  • Repository (repo): the whole project folder — code, reports, figures, and appropriate data
  • Commit: a labeled snapshot of the whole project at a moment
  • Diff: the line-by-line difference between two snapshots
  • Tag: a name attached to an important commit, such as journal-submission

Git stores commits as a chain, so your project’s history is a string of snapshots. A useful mental model is a save point in a video game. The optional extension creates a tag if time permits.

Where your changes live: three places

  • Working directory — your files as they are right now
  • Staging area — changes you’ve marked for the next commit
  • History — commits already recorded

A commit moves changes: working directory → stage → history. The staging area is the part that feels strange at first; it lets you commit some changes now and hold others back.

Why begin in the Terminal?

  • RStudio’s Git controls will be more comfortable for most everyday work.
  • Typing the commands once makes each step visible: inspect, stage, commit. It is the pencil-and-paper step before the calculator.
  • The same commands work in Posit Cloud, on a laptop, and on a server.
  • Coding agents use these commands too. Knowing them helps you inspect and correct an agent’s work later.

Then we’ll repeat the cycle with RStudio’s Git controls.

The Commit Cycle

Stage, then commit

git status              # what has changed?
git add .               # stage every unignored change here
git commit -m "Start Git practice project"  # record the staged files
  • add chooses what goes in; commit records it with a message
  • Run status before and after each Git action

Anatomy of a good commit message

  • The diff records the changed lines; the message explains the purpose of the change
  • Use a present-tense summary under ~50 characters
  • Good: Fix year parsing in cigarette data
  • Bad: changes, final, asdf
  • Write a message that will still make sense when you return six months later
  • One logical change per commit — not a whole day’s work in one blob

Use the name and email associated with your GitHub account. These become part of every commit you make in this Cloud project.

  • The first line stores the author name attached to commits.
  • The second stores the author email.
  • --global keeps each setting available throughout this Cloud project; quotation marks keep the full value together.

Run these once. They’re setup commands, and you don’t need to memorize them. Stop if the Terminal prints an error.

Task 1: Start the repository

git init
git status
  • git init creates the hidden repository in this folder.
  • git status inspects it without changing anything.

Look for On branch master, No commits yet, and Untracked files. master is the default line of history. Untracked means Git sees a file that no commit contains yet.

Where the repository lives

  • Visible project files: /cloud/project/
  • Git history and settings: hidden /cloud/project/.git/
  • Both are inside this Posit Cloud project. Nothing has gone to GitHub.

Here, local means wherever Git is running, which today is Posit’s computer rather than your laptop.

Record the first snapshot

git add . puts every unignored change in the current folder into the staging area. The period means “this folder.” It does not commit or upload anything.

git add .                              # stage the files
git status                             # confirm what is staged
git commit -m "Start Git practice project"  # record the snapshot
git status                             # confirm nothing remains uncommitted

-m supplies the quoted commit message. After the commit, Git should report that the working tree is clean.

History

Reading your history

git log --oneline

git log reads the commit history. --oneline displays each commit as one compact line.

  • Each line: a short commit ID plus your message
  • Parentheses such as HEAD -> master mark your current position; you can ignore them today
  • Plain git log shows the full author, date, and message

Seeing what changed: diff

  • git diff — unstaged changes vs. the last commit
  • git diff --staged — what you’re about to commit
  • Lines marked - were removed, + were added
  • Focus on the - and + lines; ignore the header, hashes, and permission metadata today
  • The Diff button in the Git tab shows the same thing, in color

Read the diff before every commit. It’s your last check before you record something.

What Not to Track

.gitignore

Leave large or restricted data, rendered outputs, secrets, and system files out of version control. A .gitignore file lists patterns Git should skip.

.Rproj.user/  # RStudio project state
.Rhistory     # Console command history
*.html        # every rendered HTML file
.Renviron     # may contain credentials

Commit the plain-text source that produces an output. Git can store PDFs and images, but their changes don’t produce useful line-by-line diffs.

The supplied .gitignore

Open .gitignore and read it. This project already excludes RStudio session files, rendered HTML, distributed slides, .Renviron, and the evidence workbook.

You don’t need to edit it today. Inspect .gitignore before the first commit in an unfamiliar project.
